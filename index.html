Moves the signed image into an orig- container, rewrites the signature's hashed-nodes list to follow it there and patches the node left behind under the signed name. The signature still verifies, over the copy, while the bootloader loads the patched node. This is the variant CVE-2026-33243 (barebox) and CVE-2026-46728 (Das U-Boot) cover: the patched releases reconstruct the list of signed nodes instead of trusting the property.

For FITs signed with required = "image", where a signature covers its image's data and nothing else. The signed kernel stays exactly as it is: the payload travels in an extra property of the same node and the image's unverified entry is pointed at it, so the bootloader checks the vendor's kernel and then jumps into the payload. The address asked for is where the boot script loads the FIT itself, i.e. bootm's own argument, not the kernel's load address. For a Thumb payload, add 1 to the entry afterwards. Signed configurations have entry inside the digest, so this method refuses them; use the hashed-nodes redirect there. On arm64 the image is also made to claim os = "vxworks": bootm would otherwise overwrite entry with wherever it relocated the verified kernel, and it only does that for Linux — os is no more signed than entry is. barebox is not a target: its bootm verifies through the configuration signature only, so it never reaches the per-image path this method needs.

Patches the signed image where it stands and changes nothing else: no container, no hashed-nodes rewrite. The configuration signature then covers data that no longer matches it, so verification has to fail. Use it as the control: a device that boots this image never checked the signature, and a bypass proves nothing there.

What is a FIT image?
A FIT (Flattened Image Tree) bundles the kernel, device trees and ramdisks an embedded system boots. Internally it is a Device Tree Blob (DTB). It is the native boot format of Das U-Boot, and other bootloaders like barebox support it too.
Why is FIT security relevant?
Embedded devices rely on FIT's cryptographic signatures for verified boot. Signing was bolted onto the format afterwards, though: nothing can be checked before parsing the flattened device tree, and keeping track of which bytes that signature actually covered is where it can go wrong. Those pitfalls, and how to avoid them, are what this site is about.
What does this website do?

Originally, it rewrote a signed FIT so that a bootloader verified the vendor's image and booted yours. The bytes a FIT hashes and the bytes it boots are allowed to differ, which is CVE-2026-33243 in barebox, fixed in 2026.03.0, and CVE-2026-46728 in Das U-Boot, fixed in 2026.04. You can pick what to patch:

  • /model in the signed device tree, so the booted system reports the tampering itself (cat /proc/device-tree/model)
  • the kernel, replaced by a file you supply
  • the ramdisk, with an initramfs of yours concatenated onto it, so your files land in the booted rootfs on top of the vendor's

The signature handling drop-down picks which flaw gets it past the signature; all three methods explain themselves there. Every modified FIT says so: in the injected /model, and in the signer-name of every signature node.

It has since grown further methods. Each one is a pitfall to rule out in your own boot chain: together they make it a way to check that a bootloader's verified boot is configured correctly, and not merely enabled.

Why do some images not have a signed configuration?
Not every image in a FIT belongs to a verified boot chain, and some are verified by other means: individually X.509 signed, or authenticated as one blob from outside the FIT, e.g. by i.MX HAB (High Assurance Boot).
